# Technical interview questions and answers

1. **What business problem does this represent?** Maintaining traceability and controlled ML changes in a healthcare-like workflow. The outcome is artificial; no clinical claim follows from its score (`datasets.py`).
2. **How is the dataset versioned?** A seeded generator creates canonical CSV bytes; SHA256 identifies each immutable snapshot. Loads recheck bytes and manifest (`snapshot`, `load_snapshot`).
3. **How do you prevent subject leakage?** Stratified disjoint 60/20/20 IDs are saved with prepared arrays and explicitly checked before training and candidate verification (`experiments.py`, `candidate_validation.py`).
4. **Where is scaling fitted?** StandardScaler sits inside the logistic pipeline, fitted independently within each training CV fold. Validation and test are transformed using train-fitted statistics.
5. **How are the algorithm and threshold chosen?** Five-fold train CV is reported; validation ROC-AUC selects the algorithm. A validation threshold targets .85 sensitivity. Test does not select the winner.
6. **Which release metrics are enforced?** Operator config requires AUC ≥ .78, sensitivity ≥ .75, specificity ≥ .40, Brier ≤ .20 and numeric parity ≤ 1e-12 (`experiments.gate`).
7. **What is the result?** The recorded synthetic fixture gives test AUC .86698 LR and .83770 RF, with LR selected by validation. These are artificial-data measurements, not clinical evidence.
8. **Why both DVC and MLflow?** DVC schedules and caches pipeline outputs; MLflow tracks parameters/metrics/artifacts and registry versions. `check_tracking.py` cross-checks model hashes with DVC output when present.
9. **What does the reproduction test do?** It checks normal/no-op/forced execution, seed invalidation and previous output checkout, comparing dataset and numeric model identities (`check_dvc.py`).
10. **What provenance is captured?** Commit, dirty state, selected source hash, environment versions, dataset/model digests and parameters. This is not a signed complete supply-chain attestation (`experiments.run`).
11. **Can training deploy a model?** No. Publication may log rejected candidates. Approval and verified deployment are explicit operator actions (`tracking.publish`, `lifecycle.py`).
12. **How is approval validated?** Fetch the version, verify numeric structure/hash, dataset/report/evidence consistency, recomputed metrics and clean-training check, then apply local policy (`Governance.approve`). Registry/operator evidence is a trust boundary.
13. **What determines the active model?** PostgreSQL's single deployment row joined to an approval. The MLflow champion alias is a reconciled view, not serving authority (`Governance.active`).
14. **Why use an outbox?** PostgreSQL and MLflow do not share a transaction. Pointer, audit and outbox commit together; reconciliation serializes and writes the current pointer to MLflow (`switch`, `reconcile`).
15. **How does rollback work?** Fetch an approved pinned version, verify digest, switch the pointer, probe actual readiness and prediction, reconcile alias and audit success (`verified_switch`).
16. **What if deployment verification fails?** Compensate to the prior approval; expected generation prevents overwriting a subsequent concurrent deployment. The incident is recorded, not silently ignored.
17. **What if MLflow alias update fails?** The PostgreSQL pointer remains authoritative and an uncompleted outbox can be retried. CLI `reconcile` repairs alias state without replaying a stale version.
18. **Why numeric JSON rather than pickle?** It avoids executable model deserialization. LR arrays and bounded RF topology are validated. The installed `pyfunc.py` loader is trusted code; untrusted loaders are outside the architecture.
19. **What subtle inference bug did you test?** sklearn casts tree inputs to float32 but compares as doubles. NumPy 2 scalar promotion can round a threshold; converting row values to Python float preserves the branch (`scoring.py`, `test_scoring_boundary.py`).
20. **What happens when artifacts are corrupted?** Loader checks the approved digest and cached bytes on every request; readiness and prediction fail with 503. The live acceptance corrupts/restores cache to verify this.
21. **How do API and audit protect data?** Strict finite bounded schemas, forbidden extra fields, 1 MiB actual-body limit, constant-time bearer comparison, redacted validation errors and aggregate prediction counts. No raw feature windows are stored in audit (`serving.py`).
22. **Can the API promote a model?** Its PostgreSQL serving role has SELECT and event INSERT privileges, not deployment UPDATE or approval INSERT. Live acceptance attempts a forbidden pointer update.
23. **Is the audit immutable?** UPDATE/DELETE trigger and role restrictions protect normal application use. A database owner/superuser or host operator can bypass these; it is not cryptographic/WORM storage.
24. **How do you distinguish drift from performance loss?** KS+PSI checks input/prediction distributions. Performance needs supplied aligned binary labels and compares AUC to a reference. Without labels it is unavailable; small windows are inconclusive (`monitor_windows.py`).
25. **Does a drift alert retrain or rollback automatically?** No. Reports and incidents inform the operator. `inspect_window` writes Evidently HTML/JSON and aggregate events; promotion remains separate.
26. **What monitoring is actually integrated?** API counters/histograms/gauges, Prometheus scrape and drift rule, Grafana datasource/dashboard provisioning, actual Evidently reports. Browser rendering must be separately captured, not inferred from API success.
27. **How is persistence tested?** Live acceptance recreates containers without deleting named volumes and rechecks served version, audit history, MLflow run/artifact and Grafana dashboard (`validate_phase4.py`). This is not a backup restore test.
28. **Are dependencies secure?** No clean audit is claimed. Three raw findings represent duplicate DiskCache CVE-2025-69872 plus NLTK CVE-2026-81726; current metadata provides no fixed versions. CI/CD audit remains blocking.
29. **How is CI separated from CD?** Hosted target CI installs the hash lock, tests/lints/types, builds Compose and runs integration/reproduction/audit. Explicit CT/CD needs a local labelled runner and protected environment. Remote runs are pending authorized publication.
30. **What would you improve for a real MedTech deployment?** Governed representative data and clinical evaluation first; enterprise IAM, signed approvals/artifacts, separate locked service images, TLS, backups/restores, independent validation, notification routing, cloud HA and observability SLOs. None is claimed implemented here.
